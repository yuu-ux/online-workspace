# 実装計画メモ

## 結論

今回の方針は、既存MVPをそのまま拡張するのではなく、要件定義と画面遷移図を正として最終版の設計に寄せて作り直す。

ただし、リポジトリ全体を捨てるわけではない。既存MVPは参考実装および再利用可能な部品として扱い、使える部分だけ移植する。

## 背景

現状のMVPは、Spring Boot + Thymeleaf + MyBatis + PostgreSQL で作られた簡易的なオンライン作業スペースアプリである。

MVPで実装済みの主な機能は以下。

- ユーザー登録 / ログイン
- ルーム一覧
- ルーム作成 / 参加 / 退出
- ルーム内チャット
- WebSocketによるリアルタイム更新
- 画面内通知
- プライバシーポリシー / 利用規約

一方、最終版の要件では以下のように、MVPよりかなり広い機能が必要になる。

- フレンド機能
- ルーム設定
- システム監視
- マイページ / プロフィール編集 / 退会

また、最終版のフロントエンドはGleam + Lustre + Tailwind CSSを前提としているが、現状の実動作部分はThymeleaf中心である。

## 判断

### 採用する方針

- 要件定義と画面遷移図を正として、最終版向けのDBスキーマとAPIを設計する
- API設計はOpenAPIを採用し、バックエンドとフロントエンドの契約を先に固定する
- Swagger UIを導入し、OpenAPI仕様をブラウザ上で確認できるようにする
- Gleamを本体UIとして実装する
- Spring BootはAPIサーバー寄りに移行する
- 既存MVPのコードは、認証、WebSocket、ルーム/チャット処理など、使える部分だけ移植する
- Thymeleaf画面は最終版UIの中心にはしない

### 採用しない方針

- MVPのソースコードを正としてDBスキーマを作る
- Thymeleafの画面をそのまま増築して最終版にする
- 詳細設計書を完全に作り切ってから実装に入る
- 実装後にAPI仕様を後追いで書く

## 理由

### DBスキーマの差が大きい

現状のMVPスキーマは以下の4テーブルが中心。

- users
- rooms
- room_members
- messages

最終版では、少なくとも以下のような追加設計が必要になる。

- profiles
- room_categories
- friends
- room_settings

この差分は単純なカラム追加ではなく、ドメイン設計の見直しが必要な規模である。

### ルーム参加ロジックの前提が違う

現状MVPのルーム参加時には、以下のような判定がない。

- 人数上限
- アカウント停止状態

このまま差分追加すると、後半で条件分岐が増えて保守しづらくなる可能性が高い。

### フロントエンドの前提が違う

要件ではGleam + Lustre + Tailwind CSSが前提だが、現状の実装済み画面はThymeleafである。

そのため、画面はGleamで作り直し、既存Thymeleafは画面構成や挙動確認の参考として使う。

## 詳細設計について

フルの詳細設計書を完成させてから実装に入るのは、スケジュール的に重い。

2026年7月10日までに実装完了を目指すため、最初に作るべきものは重厚な詳細設計書ではなく、実装に必要な最小設計である。

最初の1-2日で以下を作る。

- テーブル一覧
- 主要ER設計
- API一覧
- 画面ごとの必要データ
- 認可ルール
- WebSocketイベント一覧
- MVPから移植するもの / 捨てるもの

その後は、実装しながら設計メモを更新する。

## 優先して設計するもの

### 1. DBスキーマ

DBは後から大きく変えると影響範囲が広いため、最初に要件から逆算して設計する。

優先候補テーブル。

- users
- profiles
- rooms
- room_members
- room_categories
- friends
- messages

### 2. API一覧

Gleamから利用する前提で、先にAPI境界を決める。

API仕様はOpenAPIで管理する。OpenAPIを正として、バックエンド実装、フロントエンドのAPIクライアント、レビュー観点を揃える。

Swagger UIを導入し、ローカル開発中にAPI仕様とrequest/response schemaをブラウザで確認できるようにする。

例。

- 認証
- ユーザー / プロフィール
- ルーム一覧 / 作成 / 詳細 / 参加 / 退出
- チャット
- フレンド

### 3. 画面とデータの対応

画面遷移図をもとに、各画面で必要なデータと操作を整理する。

## Issue分解方針

実装タスクは `docs/implementation_issues.md` にまとめる。

各issueは、完了条件を満たせばレビュー可能な単位にする。すべての必達issueが完了したら、要件定義上の実装完了とみなす。

issueの粒度は以下を基準にする。

- DB変更、API、フロントエンド画面、テストを含めて1つの機能が動く
- 大きすぎる機能は、基盤、API、画面に分ける
- 監視など重い機能は、最小完了条件を明確にする
- 余力対応は必達issueと分ける
